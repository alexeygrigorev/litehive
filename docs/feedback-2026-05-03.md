## Cross-cutting style rules

These appeared repeatedly across both recordings.

### R1. No inline imports

> _"Потом я смотрю, что у нас очень много нинлайн-имперс. Я в принципе
> не хочу, чтобы они у нас были. То есть, я не знаю, какой смысл у них,
> в очень редких исключениях это может быть нужно, но в целом зачем."_
> — `[part-1 L2]`
>
> _"То есть я хочу понять, зачем нам это нужно. В обычных случаях
> почему мы хотим делать импорты инлайн — это если какой-то импорт
> тяжёлый. Если это не тяжёлый, то зачем мы это делаем? Пройдись по
> всем импортам и добавь в комментарии, почему этот импорт. Во-первых,
> нужно проверить, что он действительно нужен; если не нужен, то его
> нужно вытащить наверх. И в редких-редких случаях, если действительно
> это нужно, добавить обоснование в комментарий и отключить его в
> ruff. Вообще, у нас должно быть правило в ruff, которое не даёт
> делать inline-imports. Я не знаю, почему оно исчезло. Может быть,
> какой-то агент решил, что это правило не нужно. Но, короче, у нас
> просто не должно проходить такое."_
> — `[part-1 L4–L5]`

- Default position: every import lives at the top of the module.
- Inline imports are allowed only when the import is heavy (e.g. avoiding a
  cold start cost) or breaks a circular dependency that cannot be untangled
  by reorganizing modules. Otherwise hoist them.
- "Only used in this one function" is **not** a valid reason. Hoist anyway.
  Inline imports are not a code-organization tool.
- Every remaining inline import must carry a comment explaining the actual
  reason (cycle name or cold-start path).
- Add a `ruff` rule that fails on inline imports. The reviewer noted such a
  rule existed previously and disappeared. Hypothesis: an agent silently
  dropped it. **Agents do not get to change project-level lint rules
  without explicit operator direction.** Restore the rule and protect it.

### R1b. No `from X import Y as Z` module aliasing

- Module-name aliasing in either production or test code is a smell.
  `from litehive.state import persist as workflow_module` hides the real
  module name from anyone reading the code. If you need the module, use
  the real name (`import litehive.state.persist`) and refer to symbols
  by their full dotted path.
- This applies double in tests: alias-based monkey-patching is brittle to
  refactors and disguises which module a test is actually pinning
  behavior on. The reviewer flagged this explicitly during the
  inline-import hoist work.

### R1c. Audit `if TYPE_CHECKING:` blocks

> _"Потом я смотрю, у нас есть type-checking-импорты. Зачем нам это
> нужно? Мы даже не используем как это — только для аннотаций. Мне
> кажется, что тут это можно по-красивее. Все эти импорты как-нибудь
> убрать. Посмотрите, в каких случаях можно убрать, в каких нет."_
> — `[part-1 L3]`

- Treat every `from typing import TYPE_CHECKING` import like an inline
  import: it needs a justification. The two valid ones are (a) breaking
  a real runtime cycle while still wanting the type annotation, or
  (b) a genuinely heavy module that we don't want to evaluate at all
  unless typing tools ask.
- If the same module is also imported at runtime elsewhere in the file,
  the `TYPE_CHECKING` block buys nothing — drop it and use the real
  import.
- Many `TYPE_CHECKING` blocks in this codebase are unjustified — they
  exist because something imported via runtime is also annotated and
  someone preemptively split it without checking the cycle. Audit each.

### R2. No `from __future__ import annotations`

> _"Я вижу, что у нас тут `from __future__ import annotations` — это
> вообще нужно убирать, нам не нужно совсем никак. Мы используем
> современный Python, в котором это никак не нужно."_
> — `[part-1 L22–L23]`

- The project targets a modern Python where this no-ops or actively makes
  things worse for runtime introspection.
- Remove `from __future__ import annotations` everywhere. Do not add new
  ones.

> _"Дальше `if root is not None`, и у нас большой блок-код идёт. Тут
> не хотелось бы — сделать `if root is None`, тогда мы возвращаем
> что-то простое, какое-то простое действие делаем."_
> — `[part-2 L1]`
>
> _"Если бы я тут опять же делал `if leaders is None`, и тогда что-то
> простое, а дальше продолжаю в этом, чтобы уменьшить уровень

- Replace `if x is not None: <large block>` with

### R4. No string-typed domain values

> _"Это всё должно быть где-то в домене, а не по коду разбросано."_
> — `[part-2 L4]`
>
> _"Я не знаю, мы сейчас тут используем просто string, чтобы Stage
> являлся `implementing`. Мы должны использовать доменный объект.
> Это всегда должен быть. Вообще, если ты где-то находишь Stage as
> string — это очень плохо. Нужно все такие вещи найти и поменять
> их, потому что если мы что-то поменяем, будет очень нам сложно это
> потом поддерживать."_
> — `[part-2 L23]`

- Any place that stores or compares stage/role/verdict/etc. as a `str`
  must use the corresponding domain enum/dataclass instead. This
  covers comparisons (`if stage == "implementing"`), set/dict
  membership (`if stage in {"grooming", ...}`), returns, dict keys,
  function arguments — every occurrence.
- Find every occurrence of stage strings like `"implementing"`,
  `"grooming"`, etc. and migrate them to the domain object.
- Reasoning: string-typed domain values rot silently when we rename
  things; typed values surface the regressions immediately. The
  reviewer was explicit: this is a **maintenance nightmare** if not
  cleaned up.

- Remaining ignores must carry a comment explaining the reason.

### R8. Always require docstrings on small/utility functions

> _"Вот этот бы мне хотелось — небольшие комментарии иметь docstring.
> В `write_stream_artifact` — где он используется, для чего он
> нужен. `write_text_if_changed` тоже — для чего используется, для
> чего нужен. Почему вообще эта функция существует? Какую проблему
> решает? Это мне поможет определить, может у нас есть какие-то
> ненужные функции."_
> — `[part-1 L29–L30]`

- Every function in `agents/artifacts.py`-style modules should answer:
  *what problem does this solve?*, *why does it exist?*, and *who
  calls it and for what*. Without that the reviewer cannot tell
  which functions are dead weight or how a change here ripples
  outward.
- Apply this beyond `artifacts.py`. Any function whose existence is
  not obvious from its name must have a one-line docstring
  explaining its purpose, plus a callers note when the caller is
  non-obvious or when there is more than one.
- Describe callers in **domain language**, not file paths. Say
  "the implementing stage calls this when the SWE submits a reject
  via the agent-report CLI" — not "called from
  `runner.py:387`". Code paths rot when names move; the domain
  story stays true.
- For helpers with exactly one obvious caller in the same module,
  the location alone is enough — don't churn for the sake of it.

### R10b. Findability is the criterion for module organization

> _"Давай подумаем, как по доменной [архитектуре] будет дизайн, но
> правильно эти классы располагать. То есть, что должно быть
> отдельно, что должно быть не отдельно. Это сам реши, но просто я
> немножко забыл — если мне что-то нужно будет найти, я хочу это
> максимально быстро найти."_
> — `[part-1 L11]`

- When deciding what goes where (which file, which package, where
  in `domain/`), pick the placement that lets the next reader
  locate it without having to know the project's history.
- Concretely: if a domain dataclass is hidden inside a 1400-line
  utility module, that's a findability bug — move it to
  `litehive/domain/`. If a function lives in module A but every
  caller is in module B, it should be in module B.
- This applies to renaming too. Names that hint at history
  ("fast_status", "v2_handler") cost everyone who comes later.

### R10c. Big classes split into collaborating sub-classes, not delegating shells

> _"У нас есть какой-то менеджер-worktree, который просто делегирует
> это куда-то. Я не понимаю вообще, какой в этом смысл, почему у
> нас есть класс, который делегирует исполнение функций куда-то ещё.
> А зачем это нужно? Если у нас класс, то пускай всё в классе будет.
> Если класс большой становится, то его нужно развить на под-классы,
> чтобы они друг с другом взаимодействовали. То, как мы сейчас
> делаем, мне это не очень нравится."_
> — `[part-1 L13–L15]`

- The voice note flagged the `WorktreeManager`-style pattern:
  a class whose methods all delegate to free functions. That's
  not a class, it's a namespace with extra steps.
- If a class has grown too big, the right move is to split its
  responsibilities into smaller classes that *interact with each
  other*, not to keep the outer class as a façade in front of
  free functions. Either own the behavior in methods or get rid
  of the class.

### R10d. `agents/__init__.py` (and packages generally) should be navigable

> _"Так, начинаю с агентов. Тут как бы непонятно, где у нас
> entry-point, ты вообще как файл расположен. Но может быть, потому
> что я не очень хорошо знаю, что это."_
> — `[part-1 L25]`

- Package init files are the first thing a reader sees; if a
  docstring there doesn't tell them which module owns what, the
  package fails the findability test.
- Per the existing user preference, `__init__.py` should hold
  no behavior — but it *should* hold a docstring that names
  the modules in the package and their responsibilities, so
  the reader can navigate without `grep -r`.

### R12. `root` is a workspace identity, not a "maybe a path"

> _"Stage report from subagent — стоит default value, мне это
> не нравится. Но дальше `if root is not None`, и у нас большой
> блок кода идёт. И вообще, почему root может быть None? В каких
> случаях это возможно? Мне кажется, такого не должно быть в
> принципе. Мне кажется, можно — нам нужны какую-то identity
> делать типа Workspace. И вообще зачем тут root, если у нас это
> уже в базе данных?"_
> — `[part-2 L1–L3]`
>
> _"Latest task activity entry. Зачем мы передаём verdicts? Зачем
> нам передавать verdicts, если это у нас в `domain` должно быть.
> То есть у нас получается дублирование всех этих штук."_
> — `[part-2 L3]`
>
> Follow-up clarification (post-recording, in chat): _"in most
> cases we don't even need it"_ — most internal helpers don't
> need any workspace handle at all.

The voice note hammered this **three** times:

1. **`root` is not nullable.** Wherever `root: Path | None`
   appears, the `None` case is a code smell — there is no
   meaningful "no workspace" state inside business logic. Drop
   the default, drop the optionality, drop the `if root is not
   None:` guard. Make the missing data the call site's problem.
   The only legitimate place an "is this a workspace?" check
   belongs is at the CLI/process entry point.

2. **Most internal helpers don't need `root` at all.** The
   reviewer was explicit: "in most cases we don't even need it."
   When a helper exists to do work that the SQLite store /
   `Workspace` object can already locate, the helper should
   receive whatever it actually needs (a task id, a row, a
   config snapshot) and not the workspace handle. If you
   receive `root: Path` and immediately call `connect_workspace_db(root)`
   or `load_state(root)`, ask whether the caller could just pass
   the connection / state directly.

3. **Stop threading `root` through every function.** Where a
   workspace handle *is* needed, model it as an explicit
   identity (e.g. a `Workspace` value object that holds the
   SQLite store, config, and paths). Helpers should ask for
   what they need (`workspace.tasks.get(task_id)`) instead of
   receiving a `Path` and reconstructing context inside.

The cleanup ladder:

- Step A (mechanical): every `root: Path | None = None` becomes
  `root: Path` (no default). If a caller passes `None`, fix the
  caller. Most defaults exist because of one stale test.
- Step B (drop): for each helper, ask whether `root` is
  actually used or only forwarded. If only forwarded, drop the
  parameter — push the workspace lookup up to the caller that
  has the relevant data already.
- Step C (design): introduce a `Workspace` (or similar) object
  that owns the SQLite store, config, and paths. Refactor one
  feature area at a time to take `Workspace` instead of `root`.
- Step D: the CLI / entry points are the only places that turn
  a `Path` into a `Workspace`. Internals never see `Path`.

### R11. Cover with tests before refactoring

> _"Опять же, всё это нужно сначала протестировать, а потом по
> тестам тестировать, потом рефакторить."_
> — `[part-2 L18]`
>
> _"Естественно, прежде чем убирать, что это всё должно быть по
> код-аудиту, и потом убираем код, проверяем так, чтобы не удалить
> случайно что-то важное."_
> — `[part-1 L20–L21]`

- Before any non-trivial refactor, the affected behavior must be
  covered by tests. The tests run **first**; only then do we
  rename/split/restructure/delete. The voice note was explicit:
  "first test it, then refactor — otherwise we will lose
  something important."
- This applies especially to: splitting a file into a package,
  moving a function across module boundaries, deleting code that
  *looks* unused, replacing one storage backend with another,
  changing an enum's serialized form.
- If coverage is missing, the first commit in the refactor series
  is a "characterization tests" commit that pins the current
  behavior. The refactor commits come after, with the test suite
  green at each step.
- The acceptance bar is "the test would have failed before the
  fix". A test that asserts the new shape but never failed under
  the old shape doesn't protect anything.
