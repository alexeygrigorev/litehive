# Code Review Feedback — 2026-05-03

Source: two voice notes recorded while reading through litehive code.

- Part 1: `main.py`, `worktree.py`, `fs_cleanup.py`, `attention.py`,
  `agents/artifacts.py`.
- Part 2: `agents/parsing.py`, `agents/prompts.py`.

The reviewer noted that the recordings cover only those files, but the
patterns generalize to the whole codebase. Patterns must be searched for
across litehive and addressed everywhere — see
`docs/code-analysis-2026-05-03.md` for the cross-cutting analysis.

## Cross-cutting style rules

These appeared repeatedly across both recordings.

### R1. No inline imports

- Default position: every import lives at the top of the module.
- Inline imports are allowed only when the import is heavy (e.g. avoiding a
  cold start cost) or breaks a circular dependency that cannot be untangled
  by reorganizing modules. Otherwise hoist them.
- "Only used in this one function" is **not** a valid reason. Hoist anyway.
  Inline imports are not a code-organization tool.
- Every remaining inline import must carry a comment explaining the actual
  reason (cycle name or cold-start path).
- Add a `ruff` rule that fails on inline imports. The reviewer noted such a
  rule existed previously and disappeared. Hypothesis: an agent silently
  dropped it. **Agents do not get to change project-level lint rules
  without explicit operator direction.** Restore the rule and protect it.

### R1b. No `from X import Y as Z` module aliasing

- Module-name aliasing in either production or test code is a smell.
  `from litehive.state import persist as workflow_module` hides the real
  module name from anyone reading the code. If you need the module, use
  the real name (`import litehive.state.persist`) and refer to symbols
  by their full dotted path.
- This applies double in tests: alias-based monkey-patching is brittle to
  refactors and disguises which module a test is actually pinning
  behavior on. The reviewer flagged this explicitly during the
  inline-import hoist work.

### R1c. Audit `if TYPE_CHECKING:` blocks

- Treat every `from typing import TYPE_CHECKING` import like an inline
  import: it needs a justification. The two valid ones are (a) breaking
  a real runtime cycle while still wanting the type annotation, or
  (b) a genuinely heavy module that we don't want to evaluate at all
  unless typing tools ask.
- If the same module is also imported at runtime elsewhere in the file,
  the `TYPE_CHECKING` block buys nothing — drop it and use the real
  import.
- Many `TYPE_CHECKING` blocks in this codebase are unjustified — they
  exist because something imported via runtime is also annotated and
  someone preemptively split it without checking the cycle. Audit each.

### R2. No `from __future__ import annotations`

- The project targets a modern Python where this no-ops or actively makes
  things worse for runtime introspection.
- Remove `from __future__ import annotations` everywhere. Do not add new
  ones.

### R3. Flat early-return over nested `if x is not None:` blocks

- Replace `if x is not None: <large block>` with
  `if x is None: return <something simple>` followed by the unindented
  block.
- Add this rule to `docs/code-style.md`.

### R4. No string-typed domain values

- Any place that stores or compares stage/role/verdict/etc. as a `str`
  must use the corresponding domain enum/dataclass instead.
- Find every occurrence of stage strings like `"implementing"`,
  `"grooming"`, etc. and migrate them to the domain object.
- Reasoning: string-typed domain values rot silently when we rename
  things; typed values surface the regressions immediately.

### R5. No `# type: ignore` without explanation

- Investigate every `# type: ignore[...]` and remove it if the underlying
  type can be expressed correctly. Most of them in this codebase exist
  because `PipelineState` (or similar) is being silently downcast to
  `str` — fix the source instead.
- Remaining ignores must carry a comment explaining the reason.

### R6. Don't delete artifacts

- Do not prune subagent outputs, stage logs, or any debug artifacts on
  the success path. They are valuable for retrospective debugging when
  things go wrong later.
- The current "supersede / prune" logic in `agents/artifacts.py` should
  go away unless there is a clear retention budget reason.

### R7. Move prompts out of code, into templates

- Long prompt strings should not live as Python literals. Use a
  templating engine (Jinja2 is fine) and a `prompts/` (or
  `templates/`) directory.
- Build prompts via a `PromptBuilder` (or similar) class that takes
  typed inputs, populates a template, and returns a typed object — not
  a free-form `dict[str, str]`.

### R8. Always require docstrings on small/utility functions

- Every function in `agents/artifacts.py`-style modules should answer:
  *what problem does this solve?*, *why does it exist?*, and *who
  calls it and for what*. Without that the reviewer cannot tell
  which functions are dead weight or how a change here ripples
  outward.
- Apply this beyond `artifacts.py`. Any function whose existence is
  not obvious from its name must have a one-line docstring
  explaining its purpose, plus a callers note when the caller is
  non-obvious or when there is more than one.
- Describe callers in **domain language**, not file paths. Say
  "the implementing stage calls this when the SWE submits a reject
  via the agent-report CLI" — not "called from
  `runner.py:387`". Code paths rot when names move; the domain
  story stays true.
- For helpers with exactly one obvious caller in the same module,
  the location alone is enough — don't churn for the sake of it.

### R9. Centralize side-effecting subsystems behind one module

- `git`: there should be exactly one module wrapping `git` subprocess
  calls. All other code calls into it. No raw `subprocess.run(["git", ...])`
  scattered around. Re-use existing helpers (`git -C`-style helpers)
  rather than re-implementing each call.
- Same principle applies to other side-effecting boundaries — find
  duplications and consolidate.

### R10. Move agent-specific logic next to the agents

- Anything that *runs* a subagent must live under `agents/`, not in
  files that exist for other reasons (e.g. worktree management).

### R10b. Findability is the criterion for module organization

- The voice note made this explicit: "if I need to find
  something, I want to find it as fast as possible." When
  deciding what goes where (which file, which package, where
  in `domain/`), pick the placement that lets the next reader
  locate it without having to know the project's history.
- Concretely: if a domain dataclass is hidden inside a 1400-line
  utility module, that's a findability bug — move it to
  `litehive/domain/`. If a function lives in module A but every
  caller is in module B, it should be in module B.
- This applies to renaming too. Names that hint at history
  ("fast_status", "v2_handler") cost everyone who comes later.

### R10c. Big classes split into collaborating sub-classes, not delegating shells

- The voice note flagged the `WorktreeManager`-style pattern:
  a class whose methods all delegate to free functions. That's
  not a class, it's a namespace with extra steps.
- If a class has grown too big, the right move is to split its
  responsibilities into smaller classes that *interact with each
  other*, not to keep the outer class as a façade in front of
  free functions. Either own the behavior in methods or get rid
  of the class.

### R10d. `agents/__init__.py` (and packages generally) should be navigable

- The voice note: "I look at agents/__init__.py and don't
  understand where the entry point is, how the file is laid
  out." Package init files are the first thing a reader sees;
  if a docstring there doesn't tell them which module owns
  what, the package fails the findability test.
- Per the existing user preference, `__init__.py` should hold
  no behavior — but it *should* hold a docstring that names
  the modules in the package and their responsibilities, so
  the reader can navigate without `grep -r`.

### R12. `root` is a workspace identity, not a "maybe a path"

The voice note hammered this **three** times:

1. **`root` is not nullable.** Wherever `root: Path | None`
   appears, the `None` case is a code smell — there is no
   meaningful "no workspace" state inside business logic. Drop
   the default, drop the optionality, drop the `if root is not
   None:` guard. Make the missing data the call site's problem.
   The only legitimate place an "is this a workspace?" check
   belongs is at the CLI/process entry point.

2. **Most internal helpers don't need `root` at all.** The
   reviewer was explicit: "in most cases we don't even need it."
   When a helper exists to do work that the SQLite store /
   `Workspace` object can already locate, the helper should
   receive whatever it actually needs (a task id, a row, a
   config snapshot) and not the workspace handle. If you
   receive `root: Path` and immediately call `connect_workspace_db(root)`
   or `load_state(root)`, ask whether the caller could just pass
   the connection / state directly.

3. **Stop threading `root` through every function.** Where a
   workspace handle *is* needed, model it as an explicit
   identity (e.g. a `Workspace` value object that holds the
   SQLite store, config, and paths). Helpers should ask for
   what they need (`workspace.tasks.get(task_id)`) instead of
   receiving a `Path` and reconstructing context inside.

The cleanup ladder:

- Step A (mechanical): every `root: Path | None = None` becomes
  `root: Path` (no default). If a caller passes `None`, fix the
  caller. Most defaults exist because of one stale test.
- Step B (drop): for each helper, ask whether `root` is
  actually used or only forwarded. If only forwarded, drop the
  parameter — push the workspace lookup up to the caller that
  has the relevant data already.
- Step C (design): introduce a `Workspace` (or similar) object
  that owns the SQLite store, config, and paths. Refactor one
  feature area at a time to take `Workspace` instead of `root`.
- Step D: the CLI / entry points are the only places that turn
  a `Path` into a `Workspace`. Internals never see `Path`.

### R11. Cover with tests before refactoring

- Before any non-trivial refactor, the affected behavior must be
  covered by tests. The tests run **first**; only then do we
  rename/split/restructure/delete. The voice note was explicit:
  "first test it, then refactor — otherwise we will lose
  something important."
- This applies especially to: splitting a file into a package,
  moving a function across module boundaries, deleting code that
  *looks* unused, replacing one storage backend with another,
  changing an enum's serialized form.
- If coverage is missing, the first commit in the refactor series
  is a "characterization tests" commit that pins the current
  behavior. The refactor commits come after, with the test suite
  green at each step.
- The acceptance bar is "the test would have failed before the
  fix". A test that asserts the new shape but never failed under
  the old shape doesn't protect anything.

## File-by-file findings

### `litehive/main.py`

- The `agent` command is currently registered here. Move it to its own
  CLI module (e.g. `litehive/cli/agent_cli.py` if not already, or
  similar). `main.py` should remain small and act only as the
  composition root for the CLI.
- `fast_status` function: rename to `status`. We previously had a slow
  and a fast status; the slow one is gone, so the `fast_` prefix is
  stale.
- The agent vs. non-agent dispatch logic should be split out of
  `main.py` into its own file/module.

### `litehive/worktree.py`

- File is ~1400 lines. Convert into a package (`litehive/worktree/`
  with submodules) and split the responsibilities.
- The dataclasses currently defined here should be checked: do they
  belong in `litehive/domain/`? Pattern in the rest of the codebase
  should drive the decision — make the layout consistent.
- The `WorktreeManager` (or equivalent) class delegates work to
  external functions. Decide one way: either the class owns the
  behavior in methods, or there is no class. Pick whichever makes
  reading the code easier. Don't keep a class that is just a façade
  over free functions.
- After splitting, audit which functions are still used. Anything
  unreferenced gets removed.
- The merge-resolver agent invocation lives in `worktree.py`. It must
  move next to the other agents under `agents/` — `worktree.py`
  should only call into it.
- All git-subprocess logic must move into the dedicated git module
  (R9). `worktree.py` should not call `subprocess` for git directly.
- Inspect `git checkout`-equivalent paths: there is a `cd_out` / `-C`
  helper somewhere that we are not using consistently. Standardize.
- Step ordering: code analysis first, then split, then prune. Do not
  delete code without first writing the cross-cutting analysis doc so
  we don't drop something load-bearing by accident.

### `litehive/fs_cleanup.py`

- Probably belongs inside `litehive/worktree/` (or wherever it is
  actually used). Verify call sites; then either inline or move.
- Remove `from __future__ import annotations` (R2).

### `litehive/attention.py`

- File is otherwise fine, but the persistence model is wrong: it still
  writes to disk while the rest of the system is on SQLite.
- All attention writes must go through the database, like everything
  else. No file-based attention log.
- The `MaximumAttentionLog` / `CollectorOverrider` / line-trees plumbing
  is unclear and may be dead. Drop the file-based plumbing and replace
  with normal DB writes.

### `litehive/agents/artifacts.py`

- The `prune_superseded_subagent_artifacts`-style logic should go away.
  Subagent artifacts are not allowed to be deleted (R6).
- Every public function in this file needs a docstring explaining what
  problem it solves (R8). Examples: `write_stream_artifact`,
  `write_text_if_changed`. Once docstrings exist, dead/redundant
  helpers will surface and can be removed.

### `litehive/agents/parsing.py` (`stage_report_from_subagent`)

- The signature has a default value for `root` that should not exist —
  `root` is a workspace identity. Drop the default; require it.
- Replace `if root is not None: <big block>` with the early-return
  pattern (R3). Same applies to the `latest is not None` branch
  further down.
- The `verdicts` argument duplicates what already lives in domain
  (`_REPORT_FILE_VERDICTS`). Move that constant to the domain layer
  and read it from there. Stop passing it through as a parameter.
- `# type: ignore[arg-type]` here exists because `PipelineState` is
  being passed where a `str` is expected. Make the receiver accept
  `PipelineState` and delete the ignore (R5).
- `splitlines()`-style chains used inline should be hoisted into a
  named local for readability.
- The `canonical_stage_for_directive` (or whatever is named similarly)
  one-liner needs a docstring explaining whether it has multiple
  callers and what invariant it expresses; otherwise inline it.
- Reject reasons constructed inline: handle the "missing field"
  failure mode separately, not as another generic reject. And: if
  the agent receives such a reject, what is the agent expected to do
  next? The current behavior is unclear and probably wrong.
- Hoist `failure_diagnostics` and similar inline strings into named
  local variables.

### Non-completion handling in `parsing.py` / lifecycle

- Treating "agent finished without a verdict" as a `Reject` is the
  wrong model. We should *resume the same session* and ask the agent
  to continue, passing the existing session ID — the agent must keep
  its prior reasoning context.
- The reviewer has flagged this multiple times. Restating the
  preferred design:
  - the same session ID must be reused;
  - the agent receives a "you didn't submit a verdict, please report
    now" prompt as a new turn on that session, not a fresh start;
  - the state machine has the responsibility to keep the session
    alive across this nudge.
- The current `AgentNode` implementation has a `NudgeRequired`
  pathway — verify it actually reuses the session and that the parser
  layer is not silently turning the case into a `Reject` somewhere
  upstream of the node.

### `litehive/agents/prompts.py`

- File is too big and too dense. Move every prompt body to
  `prompts/` (or `templates/`) as Jinja templates (R7).
- Build a typed `PromptBuilder`. Each input the prompt needs should
  be a typed field on the builder, not a free-form dict slot.
- Audit every key currently put into the prompt and decide whether
  the agent actually needs it:
  - `task_type` — useless. The string is supposed to be a
    "categorization" but is just a free-form `str`. **Remove.**
  - `workspace_content` — currently a `str`. Replace with a typed
    object that knows how to render itself. The reader should be able
    to tell, from the type, what's actually in the prompt.
  - `registry_mode`, `routing_mode`, `share_stage`, `role_mode`,
    `source_of_truth`, `task_source_of_truth`,
    `verification_discipline`, `process_profile`,
    `workspace_overlay`, `prompt_default`, `prompt_focus`,
    `role_focus`, `missing_criteria.reason`,
    `runner_hook_prompt_lines`, `format_runner_hook_prompt_entry`,
    `runner_hook_top_section`, etc. — each one needs either a
    docstring on the field saying what it does and why the agent
    needs it, or it gets removed. Today the reviewer cannot tell
    which are load-bearing.
- `stage_owner_for_stage` and similar lookups should not exist as
  ad-hoc text snippets. They belong on the domain object — e.g.
  `Stage.GROOMING.owner`. Move all such bits of prose into domain
  attributes/methods.
- Prompts must begin with a clear role assertion: "You are a
  software engineer", "You are a tester", etc. Restructure templates
  so the role line is up front.
- State (current pipeline state, recent activity, etc.) belongs in a
  dedicated section of the template, not interleaved with role
  description.
- Remove inline imports inside this file (R1).
